# 11 · 开发守则

> 推进过程中的注意事项。写代码、改设计之前先看这里。

---

## 三条首要原则

| 原则 | 一句话 |
|---|---|
| **优先参考成熟的开源项目和代码** | 动手前先查有没有现成的；能用成熟的，就不自己从零写 |
| **时刻保持整体架构清晰** | 目录就是子系统，依赖只朝一个方向，先改文档再改代码 |
| **时刻保持代码可读** | 名字说清楚、函数短小、类型写全，注释写"为什么" |

---

## 1. 优先参考成熟的开源项目和代码

### 1.1 动手前先查

实现一个功能之前，按这个顺序找：

1. **Python 标准库**里有没有？比如读 TOML 用 `tomllib`；
2. **成熟的第三方库**有没有？比如文件锁用 `filelock`；
3. **成熟的开源项目**里有没有类似的做法？比如拟人说话参考 MaiBot。学它的思路，优先移植代码；
4. 都没有，才自己写。

**例外**：本项目的核心部分——身体信号的计算、反馈的更新规则、注意力的策略——是我们自己的设计，代码自己写。但写之前也要先看看别人（论文和项目）是怎么做的。

### 1.2 怎么判断"成熟"

| 看什么 | 标准 |
|---|---|
| 活跃度 | 最近几个月还有更新；已归档、长期没人维护的不用 |
| 许可证 | 和我们兼容，见 1.4 |
| 文档和社区 | 有像样的文档，用的人多，出了问题搜得到答案 |
| 平台支持 | 支持 Windows |
| 依赖 | 不会拖进来一大堆别的东西 |

### 1.3 三种用法，要求不同

| 用法 | 是什么 | 要求 |
|---|---|---|
| 依赖 | 用 uv 安装，不改它的源码 | 锁定版本；外面包一层我们自己的接口，以后换掉不影响核心（比如 A_memorix） |
| 移植 | 把别人的代码复制进来再改 | 文件开头注明来源链接、原许可证、我们改了什么；登记到第三方清单 `THIRD_PARTY.md`（第一次移植时创建） |
| 参考 | 只学思路，代码自己写 | 在注释或文档里写明参考了谁 |


### 1.4 许可证速查

我们自用没有约束；以后如果公开发布，整体用 AGPL-3.0（见 D12）。所以拿来的东西要和它兼容：

| 许可证 | 能不能用 |
|---|---|
| MIT、BSD、Apache-2.0 | 可以 |
| GPL-3.0、AGPL-3.0 | 可以 |
| LGPL、MPL-2.0 | 一般可以，用之前确认一下 |
| GPL-2.0-only | 不行，和 GPL-3.0、AGPL-3.0 不兼容 |
| 没写许可证、自定义的限制性许可证 | 不行 |

### 1.5 外部代码也要读懂

- 不复制自己看不懂的代码；
- 安装新依赖前确认包名拼写正确，防止装到冒名的恶意包；
- 新增依赖要说明为什么需要它。

## 2. 时刻保持整体架构清晰

### 2.1 目录就是子系统

代码目录和 [README](../README.md) 的"子系统一览"一一对应：

```text
AureusBot Project/
├── aureus/                 代码（Python 包）
│   ├── core/               启动、关闭，把各子系统组装起来
│   ├── common/             真正通用的小工具：时钟、配置、日志
│   ├── identity/           身份
│   ├── body/               身体
│   ├── hormones/           激素
│   ├── mood/               心情
│   ├── timeline/           时间线
│   ├── memory/             记忆
│   ├── people/             人际
│   ├── heartbeat/          心跳
│   ├── attention/          注意力
│   ├── agenda/             日程
│   ├── organs/             器官
│   ├── actions/            行动
│   ├── feedback/           反馈
│   ├── channels/           通道（terminal/、web/ ……）
│   ├── safety/             安全
│   ├── monitor/            观察台（D64）
│   ├── lab/                实验台（D82）
│   └── tools/
│       └── migrate/        迁移工具：盘点 MaiBot 等外部数据来源（见 13 号文档）
├── tests/                  测试，按子系统分目录
├── scripts/                开发用的小脚本，比如一条命令跑完检查
├── config/                 配置模板（用户的个人设定不进 git）
├── aureus_home/            用户配置和运行数据（不进 git，源码运行的默认数据根目录）
└── docs/                   设计文档
```

做到哪个子系统才建哪个目录，不提前建空目录。

### 2.2 依赖只朝一个方向

| 规则 | 原因 |
|---|---|
| `common` 不依赖任何子系统 | 它是地基 |
| `organs` 和 `channels` 不依赖任何状态子系统 | 器官只给建议，通道只做翻译，见 D6 |
| `safety` 依赖 `organs` 和 `timeline`，反过来不行（`organs` 不依赖 `safety`、`timeline`） | 网关包着器官，器官不知道谁在记账，见 D40；已写成 import-linter 规则 |
| 子系统之间只用对方的公开接口（`__init__.py` 里导出的东西） | 内部实现可以随便改，不牵连别人 |
| 只有 `core` 负责组装所有子系统；`heartbeat` 负责每一拍的调度顺序 | 谁在指挥，一眼就能看出来 |
| 观察台只读，不写任何状态 | 看的时候不能改变被看的东西 |

其中依赖方向的规则写成 import-linter 的检查规则，提交前自动检查，违反了就过不去；"只用公开接口"靠代码审查把关。

### 2.3 每份数据只有一个用户

数据库里每张表只属于一个子系统。别的子系统想写，要调用这个子系统的接口。比如所有子系统都通过时间线的接口追加记录，没有谁直接往时间线的表里插数据。

### 2.4 先改文档，再改代码

- 要动子系统的边界、数据怎么流、加新子系统，先在 docs 里写清楚，在 [10-decisions.md](10-decisions.md) 登记，再写代码；
- 代码和文档对不上时，先讨论哪个对，再两边一起改。

### 2.5 不提前设计"以后可能用到"的东西

- 先写最简单、能跑的版本；
- 同样的东西出现第二次、第三次，再考虑抽象成通用的；
- 例外：第一部分的实验能力（时钟、假器官、开关）从 Phase 0 起就要有，见 [12-kernel.md](12-kernel.md) 第 6 节。

### 2.6 每个阶段结束时做一次架构检查

- [ ] 目录和子系统还是一一对应吗？
- [ ] import-linter 全部通过吗？
- [ ] 有没有子系统偷偷读写别人的数据？
- [ ] 器官有没有直接写状态？
- [ ] 文档和代码对得上吗？
- [ ] 有没有往数据根目录之外写东西？有没有无上限增长的数据？（见 14 号文档第 6 节，D38）

## 3. 时刻保持代码可读

### 3.1 名字

- 用完整的英文单词，和 [术语表](09-glossary.md) 一致：写 `energy`，不写 `e`、`eng`；
- 函数名以动词开头：`compute_energy()`、`append_event()`；
- 布尔值用 `is_`、`has_` 开头：`is_asleep`、`has_budget`；
- 常量全大写：`DAILY_RESET_HOUR`。

### 3.2 短小

- 一个函数只做一件事，超过 50 行左右就考虑拆开；
- 一个文件只放一类东西，超过 400 行左右就考虑拆开。

### 3.3 类型写全

所有函数的参数和返回值都写类型注解。Python 不强制，但写了以后 pyright 能在运行前查出类型错误，读代码的人也一眼知道该传什么、会返回什么。

### 3.4 注释怎么写

**要写的**：

- **每个文件开头**：这个文件属于哪个子系统、负责什么；
- **每个公开的函数和类**：docstring，说明做什么、参数、返回值、可能抛出的错误；
- **"为什么"**：为什么用这个公式、这个阈值、这种做法。和设计原则或决策有关的地方，写上出处，比如"见 D6"、"见 04-body-signals.md 第 4 节"；
- **移植来的代码**：来源、原许可证、改了什么。

**不要写的**：

- 重复代码本身的话，比如 `i += 1  # i 加 1`；
- 过时的注释。改代码时同步改注释——和代码对不上的注释比没有更糟。

**语言**：注释和 docstring 用中文，变量名、函数名用英文。

### 3.5 示例

```python
def compute_energy(today_budget: Decimal, today_spent: Decimal) -> float:
    """计算精力：今日剩余额度占今日额度的比例。

    规则见 docs/04-body-signals.md 第 4 节。

    Args:
        today_budget: 今日额度，单位：元。
        today_spent: 今日已花费，单位：元。

    Returns:
        0.0 到 1.0 之间的精力值。
    """
    if today_budget <= 0:
        # 额度为 0（比如月预算已经用完）时，直接视为没有精力，
        # 而不是去做除法报错。这对应"透支保护"档。
        return 0.0
    # 钱用 Decimal 而不用 float：float 有舍入误差，账会越算越偏。
    remaining = max(today_budget - today_spent, Decimal("0"))
    return float(remaining / today_budget)
```

### 3.6 不出现"魔法数字"

阈值、间隔、比例这类数字，不直接写在代码里，而是放进配置文件，或者定义成有名字的常量，并注明含义和出处：

```python
# 每天几点重算预算（"睡一觉，精力恢复"），见 04-body-signals.md 第 4 节。
DAILY_RESET_HOUR = 4
```

### 3.7 出错时：让问题暴露，行为朝安全倒

- 不要用 `except Exception: pass` 把错误吞掉；
- 出错时做三件事：记日志；记入时间线，让"压力"信号知道；选择安全的做法；
- 不要编造默认值来掩盖问题。比如读不到预算数据时，不能假设"还有钱"，要按"没钱"处理。

### 3.8 交给工具

| 工具 | 管什么 |
|---|---|
| ruff | 统一格式，查出常见错误 |
| pyright | 类型检查 |
| import-linter | 架构规则 |
| pytest | 测试 |

Phase 0 就把它们配好，一条命令全部跑完。提交前必须全部通过。

## 4. 其他注意事项

### 4.1 小步走

- 每一步都能运行、能验证，一次只改一件事；
- 先跑通，再优化。

### 4.2 测试

- 每条设计规则都要有测试，比如"时间线只能追加"、"花费不能超过上限"、"器官不能写状态"；
- 阶段的验收标准尽量写成自动测试。测试也是"活的文档"。

### 4.3 git

- 每完成一个能运行的小步，检查全部通过后提交一次，方便回退；
- 提交信息用中文写清楚做了什么；
- 实验性的改动开分支做；
- `.env`、`secrets.vault`、`secrets.key` 和 `data/` 永远不提交。

### 4.4 省钱

- 开发和调试时，优先用假器官和便宜模型；
- 开发环境单独设一个较低的 token 上限（D37）。

### 4.5 实验可复现

实验的配置、随机种子和结果一起保存，拿同样的配置能跑出同样的结果。
