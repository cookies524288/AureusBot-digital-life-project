## 目标和验收

目标：没人找它时，它会因为真实的原因（好久没好好聊、答应的事到期了）主动找用户说话；对方不回就退避，不刷屏。默认关闭。

路线图验收：每次主动联系都能说出真实原因；对方不回应时退避，不刷屏。D76 的验收逐条见「自检清单」。

### 身体：社交需求（`aureus/body/signals.py`）

```python
@dataclass(frozen=True)
class SocialNeedReading:
    enabled: bool
    level: float = 0.0          # [0, 1]
    hours_since: float | None = None  # 距上次有效对话几小时；从没好好聊过时是 None
    high: bool = False

def compute_social_need(
    last_conversation_at: datetime | None, now: datetime, config: BodyConfig
) -> SocialNeedReading
```

- 关掉时：`SocialNeedReading(enabled=False)`。
- `last_conversation_at is None`（从来没好好聊过）：`level = 1.0`、`hours_since = None`、`high = True`。理由写在注释里：没有聊过就是最想聊的时候；反正主动联系默认关，打开后还要知道用户在哪个通道才会真的开口。
- 否则 `elapsed = max(0, (now - last).total_seconds())`，`level = 1 - exp(-elapsed / (常数小时 × 3600))`，`high = level >= social_need_high_at`。
- `Body.read(self, backlog: int = 0, last_conversation_at: datetime | None = None)`，`BodyReading.social_need: SocialNeedReading`。时间用 `self._clock.now()`。
- **不改** body_samples 表（观察台 2.12 再加）。

### 把关纯函数（`aureus/heartbeat/initiative.py`，新）

不 import 心跳主循环；只用标准库、`aureus.common`、`aureus.body` 的类型。

```python
@dataclass(frozen=True)
class InitiativeState:
    """主动联系的历史，心跳在内存里维护、重启时从时间线还原。"""
    contacts_today: int = 0
    last_considered_at: datetime | None = None   # 上一次考虑（不管说没说）
    unanswered_streak: int = 0                    # 连续没回应的次数
    pending_since: datetime | None = None         # 已发出、还在等回应的那次的发出时刻

@dataclass(frozen=True)
class InitiativeDecision:
    allowed: bool
    blocked_by: str            # 不允许时一句中文原因，允许时空字符串（只写日志，不进时间线）
    reasons: tuple[str, ...]   # 允许时：给规划器和时间线的真实原因，至少一条

def next_interval(streak: int, config: InitiativeConfig) -> timedelta
    # min_interval_hours × 2^streak，最多 max_interval_hours

def daily_limit(config: InitiativeConfig, *, cautious: bool) -> int
    # cautious 时 max(1, max_per_day // 2)，否则 max_per_day

def decide(
    *,
    now: datetime,
    config: InitiativeConfig,
    state: InitiativeState,
    social_need: SocialNeedReading | None,   # 没有身体时 None
    due_items: Sequence[str],                 # 用户名下已到期约定的描述，比如 "#3 提醒他开会"
    effective_tier: EnergyTier | None,
    night: bool,
    halted: bool,
    busy: bool,                 # 有想法在跑，或者收件箱 / 待收消息不空
    cautious: bool,
    has_channel: bool,          # 这次运行里用户说过话（知道往哪发）
) -> InitiativeDecision
```

`decide` 按下面顺序判断，第一个不满足的就返回 `allowed=False` 和对应的 `blocked_by`：

1. `config.enabled`；
2. `not halted`；
3. `not busy`；
4. `not night`；
5. `effective_tier` 是 `None`、`NORMAL` 或 `UNLIMITED`；
6. `has_channel`；
7. `state.unanswered_streak < config.give_up_after`（到了就停，等用户先开口）；
8. `state.pending_since is None`（上一次还在等回应时不再找）；
9. `state.contacts_today < daily_limit(config, cautious=cautious)`；
10. `state.last_considered_at is None` 或 `now - last_considered_at >= next_interval(state.unanswered_streak, config)`；
11. 有原因：社交需求开着且 `high`，或者 `due_items` 不为空。都没有就 `blocked_by = "没有要找的理由"`。

原因文字（`reasons`，代码生成，不经模型）：

- 社交需求偏高：`f"距上次和用户好好聊过 {N} 小时，社交需求 {level:.0%}"`，从没聊过时 `f"还没和用户好好聊过，社交需求 {level:.0%}"`；
- 每条到期约定一条：`f"答应的事到期了：{描述}"`。

### 主动规划的提示词和解析

`aureus/heartbeat/context.py`：

```python
def build_initiative_plan_prompt(
    history: Sequence[TimelineRecord], user_name: str, reasons: Sequence[str],
    timezone: tzinfo | None = None,
) -> str
```

内容：最近的对话记录（复用 `_dialogue_line`；没有记录时写「还没有聊过」）；然后「现在没人找你。你在考虑要不要主动找{user_name}说话，真实的原因是：」加每条原因；然后格式说明，只输出一个 JSON：`{"reach_out": true 或 false, "intent": "想说什么，一两句", "reason": "为什么这样决定，一句话"}`，并说明「没有真正想说的就写 false，不要硬找话题；不要编造原因以外的理由」。

`build_system_context` 新参数 `initiative_note: str = ""`，非空时作为一段放在最后。心跳给回复器的说明是：`f"【主动联系】这是你主动找{user_name}，不是在回复。原因：{'；'.join(reasons)}。被问起为什么找他，就照实说这些原因。"`

`aureus/heartbeat/planning.py`：

```python
@dataclass(frozen=True)
class InitiativePlan:
    reach_out: bool
    intent: str
    reason: str
    def to_metadata(self) -> dict[str, Any]

def parse_initiative_plan(text: str) -> InitiativePlan | None
```

规则照 `parse_plan`：超过 4000 字、没有 JSON、`reach_out` 不是真正的布尔值、`reach_out` 为真却没有 `intent` → `None`。**看不懂时当作不说**（朝不打扰的方向倒，和回复时「拿不准就回」相反，注释写明理由）。

主动回复用 `build_reply_prompt`：`history` 是最近对话，`new_messages` 为空不行（它要求至少一条）——新增一个参数或新函数 `build_initiative_reply_prompt(history, user_name, timezone, intent)`，提示词写「你要主动开口，想表达的意思是：{intent}。请直接写出你要说的话，不要加名字或时间前缀。」。长度按这次做法的 `length_limit`，没有就「短」。

### 心跳（`main_loop.py`）

构造参数新增：`initiative: InitiativeConfig | None = None`、`calendar: BudgetCalendar | None = None`（用来算「今天」；不给就 `BudgetCalendar(timezone)`）。

状态：
- `self._last_conversation_at: datetime | None`：上次有效对话的时刻。在 `_collect_finished_thought` 里**真正把回复发给 VERIFIED_USER 的那一刻**设成 `self._clock.now()`（规划器决定不回、急停拦下、器官失败都不设）。
- `self._initiative_state: InitiativeState`。
- `_read_body` 调 `self._body.read(backlog, self._last_conversation_at)`。

用户的回复也要标出来，方便重启还原：回复的消息 metadata 加 `"to_user": True`（`target.trust is TrustLevel.VERIFIED_USER` 时）。它表示目标是用户，送达由独立收据确认。普通回复和主动消息都先追加 `EVENT_MESSAGE`，带 `delivery_pending: true`；落盘调用失败就不发送，包括数据库已提交但调用报错的情况。发送后追加私密的 `EVENT_MESSAGE_DELIVERY = "message_delivery"`，metadata 为 `{message_id, delivered}`。收据时间取通道返回后的注入时钟，不改写原消息。

`delivery.py` 提供 `read_delivery_receipt(timeline, message) -> TimelineRecord | None` 和 `read_message_delivery(timeline, message) -> bool | None`：按消息编号查收据，没有收据时为未知。收据写入失败不重发；本次运行仍按实际发送结果更新有效对话，重启无法证实时保守忽略。新格式未确认送达的消息也不作为已说出口的历史交给器官。

每拍（`beat` 里，放在 `_maybe_start_thought()` 之后，这样用户消息总是优先）：`_maybe_start_initiative()`：
1. 先结算等回应超时的：`pending_since` 不为空且 `now - pending_since >= answer_window` → 写 `initiative_result`（`answered: false`、`considered_id`），已证实送达时反馈记失败，`unanswered_streak += 1`，`pending_since = None`。发送未知时只结束保守等待，结果另标 `delivery_confirmed: false`，不新建反馈预期或结算反馈。
2. 跨天了（用 calendar 比较 `last_considered_at` 和 `now` 是不是同一天）就把 `contacts_today` 清零。
3. 调 `decide(...)`：`busy = self._thought is not None or bool(self._unanswered) or bool(self._pending)`；`has_channel = self._last_user_contact is not None`；`due_items` 取 `self._agenda.open_items(用户的 person_id)` 里 `is_due(now)` 的，描述 `f"#{id} {content}"`（没有日程或认不出用户时为空）；`cautious` 取 `self._mood.cautious`（没有心情时 False）；`effective_tier` 取 `self._current_strategy().effective_tier`；`night` 取读数里的 `sleep.night`（没有身体时 False）；`halted` 取急停状态。
4. 不允许：只在 `blocked_by` 变了时记一行 debug 日志，不写时间线（免得每拍刷）。
5. 允许：先更新 `last_considered_at = now`，再开后台任务 `_initiate(job)`，放进 `self._thought`（同一时间只想一件事）。

用户的 person_id：用 `self._people.find(*_conversation_of(self._last_user_contact))` 取；没有人物档案时为 None。

后台任务 `_initiate`（不写任何状态，只返回结果，和 `_think` 同样的规矩）：
1. 用 `self._config.plan_organ`（和 `_plan` 同一个器官）调规划器，`CallPurpose.OPTIONAL`，系统上下文用和回复用户时一样的 `build_system_context`（带身体、激素、心情、好感、日程摘要），提示词是 `build_initiative_plan_prompt`。被网关拒绝、调用失败、看不懂 → 结果「不说」，原因记下来。
2. `reach_out` 为真：调回复器（`CallPurpose.OPTIONAL`），系统上下文多带 `initiative_note`，提示词是主动回复的那个。空回复、失败 → 不说。
3. 返回一个结果对象（自己定名字，比如 `_InitiativeOutcome`：`plan`、`response`、`failure`、`reasons`）。

`_Thought` 的处理：`_Thought` 现在要求 `replying_to`。做法二选一（推荐 a）：
- a. `_Thought` 加字段 `kind`（回复 / 主动）和 `initiative_reasons`，主动时 `replying_to` 是空元组；`_collect_finished_thought` 开头按 `kind` 分到 `_collect_initiative(thought)`；`_record_abandoned` 对主动想法不发通知（它本来就没在回谁）。
- b. 另开一个任务槽。不推荐：要处理两个后台任务同时跑。

`_collect_initiative`（顺序固定：先发，再写考虑记录，这样 `sent` 能如实填）：
1. 只有决定说并且拿到了回复文字，才发：权限检查 `ACTION_REPLY_TO_USER`（急停中就不发，`decided` 记 `"failed"`、`failure` 写权限原因）；先写 `EVENT_MESSAGE`（actor ME，可见范围用 `self._last_user_contact.visibility`，metadata 带 `"initiative": True`、`"reasons": [...]`、`"to_user": True`、`"channel"`、`"delivery_pending": True`）；落盘成功后用 `_deliver_reply(self._last_user_contact, text)` 发出，追加送达收据；实际发出才记反馈预期（`PROACTIVE_CONTACT`，把握取这一类当前自信，没有数据用 `PRIOR_CONFIDENCE`，`source_id` 是这条消息的序号）。
2. 再写 `initiative_considered`（只有自己可见）：metadata `reasons`（列表）、`social_need`（数字或 None）、`due_item_ids`、`decided`（`"reach_out"` / `"skip"` / `"failed"`）、`sent`（真的发出去了才是 True）、`plan`（`InitiativePlan.to_metadata()` 或 None）、`failure`（字符串或空）、`feedback_id`（没记反馈时 None）。
3. 发出时更新内存：`contacts_today += 1`、`pending_since` 取实际送达收据的时刻（收据写失败时用通道返回后的时钟），并记下这条 considered 的序号和反馈编号（结算回应时用）。
4. 这次主动**不**算有效对话（`_last_conversation_at` 不变：只有用户说了、它回了才算）。

用户回应：每拍先 `_take_in_perceptions`，再收器官结果，确保发送前已到的来信不被误算为回应。收到 VERIFIED_USER 的消息时：如果 `pending_since` 不为空且 `now - pending_since < answer_window` → 写 `initiative_result`（`answered: true`、`considered_id`、`message_id`），反馈记成功；用户开口立即把 `unanswered_streak` 清零，但结果未落盘前保留等待材料和原判定以便重试。持久化完成后才清 `pending_since`（D76 第 4 条、复核 R2 / R4）。

重启还原（`wake_up` 里，在 `_restore_hormones` 之后）：
- `_last_conversation_at`：只往回看最近 50 条它说的 `EVENT_MESSAGE`，排除主动消息。新格式有 `delivery_pending: true`，只有成功收据才算，使用收据时间；失败或未知均不算。旧格式继续认 `to_user: true`；没有 `to_user` 时看 `in_reply_to` 指向的记录里有没有 actor USER 的，有也算，看不到就当 None。
- `_initiative_state`：读最近的 `initiative_considered`、`initiative_result` 和主动 `message`（各取最近 50 条），按下述故障恢复规则合并、去重。`contacts_today` 按实际送达时刻所属的预算日计数，未知时用来源记录的时刻保守计数；`last_considered_at` 取已恢复的最近考虑或联系时刻。`unanswered_streak` 从最近往回数连续 `answered: false` 的 result，遇到成功或后来的用户来信就停。`pending_since` 取最近尚未结算联系的送达时刻，未知时取来源时刻；结果按 `considered_id` 和 `message_id` 关联。等回应期间停了机，醒来后先补结算。
- 反馈编号：`initiative_considered` 的 metadata 存 `feedback_id`；还原 `pending_since` 时一并还原。

R1～R3、评审 A / B 的故障恢复：消息 metadata 在发送前保存 `initiative_expected` 和 `initiative_consideration` 快照，considered 和 result 均关联 `message_id`。按来源消息合并记录去重；消息和考虑的恢复窗口错位时，再按 `message_id` 精确查回窗口外的考虑记录，明确 `sent: false` 或失败收据的消息不计数。考虑记录 `sent: true`、成功收据或已存在的来源反馈可证实送达；考虑丢失但有凭据时补 `sent: true`，没有凭据时保守占限额和等待，补 `decided: "unknown"`、`sent: null`，不新建反馈预期或结算反馈。当天记录超出 50 条恢复窗口且不能证明剩余次数时，保守视为当日限额已用完。未结算记录不会因有更晚用户消息而被丢弃；取来源消息之后第一条用户消息的时刻，按恢复的实际送达窗口判定，并独立清退避。已证实送达的预期写入失败时，按来源找回或用原快照补一次，再结算；追加已成功但调用报错时，重试先查已有来源记录，避免重复反馈或结果。

### 运行时（`aureus/core/runtime.py`）

`Heartbeat(..., initiative=runtime.initiative, calendar=calendar)`。扮演模式不传 initiative（或传了也因为没有身体，`social_need` 为 None，只剩到期约定这一个原因——**要求：扮演模式下完全不主动**，所以扮演模式时传 `None`）。`[initiative] enabled = true` 而没配规划器器官（`planning_enabled = false`）时：启动只记一条警告「主动联系要用规划器」，然后当作关闭。

## 行为细则和边界情况

- 时间全部从 `self._clock.now()` 取。
- 一切读日程、读反馈、写时间线的失败：只记日志，这一拍不主动，不让心跳停下（同 `_check_agenda` 的写法）。
- 主动消息走的通道就是 `self._last_user_contact.channel`；那个通道已经断开（`_sinks` 里没有）就不发，记 `decided: "failed"`、`failure: "通道不在了"`。
- 网页和终端都是用户：哪边最近说过话就从哪边发。
- 主动想法在跑的时候用户来了消息：不打断（D61），消息进收件箱，主动想法结束后再回。
- 关闭时进行中的主动想法：照 `_settle_thought_before_shutdown` 等一会儿，等不到就取消；取消的主动想法写 `initiative_considered`（`decided: "failed"`、`failure: "关闭时取消"`），不发通知。
- 原因只能来自代码（社交需求读数、到期约定）；规划器写的 `reason` 只是它的理由，存进 metadata，不当成主动的原因。
