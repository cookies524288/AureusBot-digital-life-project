## 目标和验收

1. `working_memory_capacity` 默认 80 → 50；`working_memory_retain` 默认 25 → 20；`retain < capacity` 校验不变。
2. `_maybe_start_thought` 每轮取该批**最新** `working_memory_capacity` 条进入上下文；超出的更早消息**整批从队列移除并丢弃出上下文**，不排队到下一轮、不进入本轮请求。
3. 丢弃只针对本轮上下文：不删除时间线/收件箱原件；引用或 planner `read_platform_history` 仍能取回。
4. 工作记忆滚动摘要仍按 capacity/retain 整理，只是默认值变小；本轮截断与滚动摘要各自独立，不互相替代。
5. 取代 3.11「超出留到下一轮」的语义：超出即丢弃出上下文。
6. 防抖、提及、D145 收件箱上限、预算、权限、急停不变。
7. 不真实调用模型。

## 行为细则和边界情况

1. 取最新 N 条：按 `record.id` 升序排好后取末尾 capacity 条；丢弃的是更早的 `batch[:-capacity]`。
2. 丢弃 = 从 `_unanswered` 移除、不进入本轮 job、不留下轮；时间线/收件箱记录不动。
3. 工作记忆关闭（`working_memory_enabled=False`）时不截断（沿用现有条件）；此时仍受 D145 收件箱上限。
4. 驻留批次（`residence is not None`）不套用本截断（沿用现有 `residence is None` 条件），由收件箱 `read_latest_and_clear` 控制每轮条数。
5. 滚动摘要（`WorkingMemory`）的 capacity/retain 语义不变，只是默认变小；本轮截断不影响摘要整理触发。
6. 与 D145 叠加：收件箱每轮读最新 15 条并清空未读；工作记忆每轮上下文最多最新 50 条。两者都「取最新、丢更早」，方向一致。
7. 不真实调用模型。

## 实现备注

- **丢弃方式**：`Inbox.remove(items)` 按 `id(item)` 移除选中条目，同会话其余条目保留。
  因此 `self._unanswered.remove(batch[:-capacity])` 只丢弃更早的超出部分，最新 capacity 条
  仍留在队里，等组装成功后再由原有的 `self._unanswered.remove(batch)` 出队；没有新增队列 API。
- **测试改名**：旧名 `test_pending_replies_are_split_at_working_memory_capacity` 的「分批」语义
  与 D146 相反，改为 `test_pending_replies_above_working_memory_capacity_drop_the_oldest`；
  另新增 `test_context_keeps_only_the_latest_capacity_messages`（60 条、容量 50）。
- **默认窗口测试**：`test_default_window_rolls_and_restores` 依赖默认 80/25，已按 50/20 更新
  触发条数、整理条数和保留条数。
- **示例配置提前到第 1 个子步骤**：既有 `test_heartbeat_example_values_equal_the_defaults`
  逐项比较模板与默认值，默认改小后必须同时改模板，否则第 1 个提交的测试是红的；
  因此 `config/aureus.example.toml` 与默认值一起提交，第 3 个提交只含设置页与文档。
- **empathy/inbox review 测试**：两组用例的显式容量（20/5、4）都大于实际批次（1–2 条），
  没有触发截断，按「最新 N 条」的原有断言仍然成立，无需修改；实际运行通过。
- **与 3.62 的关系**：只改 `_maybe_start_thought` 的截断，不碰 `_take_inbox_priority`、
  `inbox_read_limit` 或 `read_latest_and_clear`；3.62 的收件箱改动保持原样。
