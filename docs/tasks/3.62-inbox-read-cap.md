## 目标和验收

1. `[heartbeat] inbox_read_limit` 默认 15（范围 1–200 不变）。
2. 每轮每会话一次读取**至多** `inbox_read_limit` 条**未读**，取**最新**的 N 条（按入箱升序返回，便于上下文）。
3. 读取后把该会话**全部未读**标为已读（水位推进到该会话当前最大入站消息 id）；更早的、没读到的未读丢弃，不堆积；下一轮从新未读开始。
4. 丢弃不删除：消息仍在收件箱与时间线；引用或 planner `read_platform_history` 仍能取回已读历史。
5. 入场选择 `count` 仍不超过 `inbox_read_limit`，语义改为「读最新 min(count,上限) 条 + 清空该会话未读」。
6. 翻阅、活跃会话补读、防抖补读、优先来信都走「读最新 N 条 + 清空」；每轮回复针对这批，不逐条追最老。
7. 取代 D116 第三、四条（不再读全部新未读、不再保留更早未读水位）。
8. 防抖、提及、预算、权限、急停、导出、账本不变。
9. 不真实调用模型。

## 接口

- `InboxStore.read_latest_and_clear(conversation: ConversationKey, *, limit: int) -> list[InboxMessage]`：返回该会话最新的 min(limit, 未读数) 条未读（id 升序），并把该会话未读清空（水位推到最大入站 id）。
- `InboxAttention.read_selection` / `active_messages` / `debounce_messages` 内部改用它；签名不变。

## 行为细则和边界情况

1. limit 用 `min(count, read_limit)`；count 非法或超上限时按 read_limit 或拒绝（沿用现有 `read_selection` 校验）。
2. 取最新 N 条：SQL `WHERE 未读 ORDER BY m.id DESC LIMIT ?`，返回前按 id 升序，保证上下文时间顺序。
3. 清空：水位 `last_read_id = 该会话 MAX(incoming m.id)`；没有未读时不改水位、返回 []。
4. 优先来信（用户/特别关心/提及）：`priority_messages` 仍先收集，但提交时按会话 `read_latest_and_clear`，保证优先来信被读到且同会话更早未读不堆积。
5. 已读历史仍可查：`platform_history.read` 走 `list_read_history`，不受水位影响；引用消息 planner 能取回。
6. 时间线 `mark_read`：水位推进后，`_take_in_perceptions` 对已读 id 的 `mark_read` 应幂等（不报错、不回退水位）；核对 `_advance_read_range` 是否会把水位拉回，必要时调整。
7. 不改 mention 1 秒、整批 8 秒、防抖档位、快速反应。
8. 不真实调用模型；测试用假器官、手动时钟。

## 实现备注

- **优先来信的改法**：保留 `priority_messages` 只读收集（D137 的身份优先、只看未读、过滤已进时间线等语义不变），
  在 `_take_inbox_priority` 提交优先批次后，按会话调用 `read_latest_and_clear` 把该会话未读水位推到最大入站消息。
  返回值不提交：这一轮只回复优先来信，同会话更早或同时段的普通未读不再逐条追赶，也不会混进优先回复，
  与设置页「优先来信单独处理」一致（D145 第三条：没读到的直接丢弃）。
- **mark_read 幂等核对**：`_advance_read_range` 从当前水位往后找连续的已确认未读，水位已经到最大入站 id 时
  找不到候选，直接不改；新到的消息不在确认集合里时也在第一个候选处停下，不会把水位拉回。无需改 `_advance_read_range`。
- `read_window` 未删除：仍被现有直读测试使用，生产心跳路径已全部改用 `read_latest_and_clear`。
- `tests/heartbeat/test_busy_group_debounce.py` 工作区原本是 LF（不是任务文档写的 CRLF），保持 LF 提交，
  避免整文件换行差异；其余改动文件保持 CRLF。
