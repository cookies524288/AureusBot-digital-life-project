# 任务文档

从路线图 2.8 起，项目把设计、实现与复审分开。设计阶段确定范围和验收标准，实现阶段按任务文档完成工作并自检，复审阶段检查设计约束与代码质量。流程依据见 [D75 与 D77](../10-decisions.md)。
每个路线图步骤一份文档，文件名是步骤号，比如 `2.8.md`。任务文档集中记录设计依据、实施范围和验收证据，并列出实现所需的参考资料。

复审以任务文档、提交和工作树为依据，按需复跑专项检查。评审意见与返工记录保存在同一份任务文档中。遇到需要维护者决定的问题时，先记录问题与依据。

## 开发资料

1. 本页和当前任务文档。
2. 任务文档开头列出的[项目决定](../10-decisions.md)与设计文档。
3. [开发守则](../11-dev-guide.md)与任务文档指定的代码和测试。

## 实施与自检

- 只做任务文档里写的事；「不做」一节里的不碰。
- 按「子步骤」的顺序做，每个子步骤 `uv run python scripts/check.py` 全绿后提交一次，提交信息用中文写清楚做了什么。
- 提交前只 `git add` 指定的文件，不用 `git add -A`；推送须经复审通过并获得维护者授权。
- 任务文档没写清楚、或者和已有决定冲突的设计问题，不自己定：写进任务文档末尾的「待设计问题」，然后停下。
- 不读 secrets.key、secrets.vault、.env，不打印密钥；不打开用户本机 MaiBot 的数据；真实模型调用须经维护者授权。
- 做完后对照「自检清单」逐条验收：在每条前面打勾 `[x]`，后面写对应的测试名或命令输出摘要；有一条打不了勾就不算交付。最后把「状态」改成「待评审」。

## 质量复审（D77）

清单里的机械项由实现的人自己核对。复审检查清单之外的：设计原则（没有装饰、器官只给建议、时间从时钟取、只追加、出错朝安全方向倒）、结构（模块边界、函数长短、命名和术语表一致、注释写为什么）、测试是否真的测到了行为、有没有多余或重复的代码。意见写进「验收意见」，交回实现的人修改。

## 任务文档的格式

```markdown
# 路线图 X.Y：标题

状态：待实现 / 实现中 / 待评审 / 待修改 / 完成
设计：DXX（docs/10-decisions.md）

## 先读
要读的决定和文档、要看的现有代码（文件路径）。

## 目标和验收
一句话目标；路线图上的验收标准逐条列出，每条对应后面的哪个测试。

## 改动一览
新增和修改的文件，各自负责什么。

## 接口
新类、新函数的名字、参数、返回值、异常；放在哪个模块；和现有代码怎么接。

## 配置
新增配置节和字段：类型、默认值、范围校验；示例配置 config/aureus.example.toml 怎么写。

## 行为细则和边界情况
逐条写清楚，包括出错时朝哪个方向倒。

## 测试
要新增的测试文件和测试用例（名字和要断言的事）。

## 子步骤
1. ……（每步完成后检查全绿、提交）

## 自检清单
- [ ] 每一条都能机械判断，写明对应的测试或命令（实现的人打勾并填结果）

## 坑
这个仓库里已知的坑（Windows、换行、测试写法等）。

## 不做
明确不在这一步做的事。

## 待设计问题
（实现的人遇到问题时写在这里，然后停下）

## 验收意见
（记录质量复审的结论与依据）
```
