# 任务文档

从路线图 2.8 起，设计和实现分开（D75）：Claude 设计并写任务文档，GPT 6.1 sol 照文档实现，Claude 验收。
每个路线图步骤一份文档，文件名是步骤号，比如 `2.8.md`。任务文档是唯一的交接物，实现的人只看它和它指名要读的文档。

## 实现的人先读

1. 本文件；
2. 任务文档开头「先读」里列出的决定（docs/10-decisions.md）和文档；
3. 开发守则 docs/11-dev-guide.md，以及仓库根目录本机的 CLAUDE.md（协作约定、设计原则、技术约定）。

## 实现时的规矩

- 只做任务文档里写的事；「不做」一节里的不碰。
- 按「子步骤」的顺序做，每个子步骤 `uv run python scripts/check.py` 全绿后提交一次，提交信息用中文写清楚做了什么。
- 提交前只 `git add` 指定的文件，不用 `git add -A`；不推送，推送由 Claude 验收后做。
- 任务文档没写清楚、或者和已有决定冲突的设计问题，不自己定：写进任务文档末尾的「待设计问题」，然后停下。
- 不读 secrets.key、secrets.vault、.env，不打印密钥；不打开用户本机 MaiBot 的数据；真实调用模型要先问用户。

## 任务文档的格式

```markdown
# 路线图 X.Y：标题

状态：待实现 / 实现中 / 待验收 / 验收通过
设计：DXX（docs/10-decisions.md）

## 先读
要读的决定和文档、要看的现有代码（文件路径）。

## 目标和验收
一句话目标；路线图上的验收标准逐条列出，每条对应后面的哪个测试。

## 改动一览
新增和修改的文件，各自负责什么。

## 接口
新类、新函数的名字、参数、返回值、异常；放在哪个模块；和现有代码怎么接。

## 配置
新增配置节和字段：类型、默认值、范围校验；示例配置 config/aureus.example.toml 怎么写。

## 行为细则和边界情况
逐条写清楚，包括出错时朝哪个方向倒。

## 测试
要新增的测试文件和测试用例（名字和要断言的事）。

## 子步骤
1. ……（每步完成后检查全绿、提交）

## 坑
这个仓库里已知的坑（Windows、换行、测试写法等）。

## 不做
明确不在这一步做的事。

## 待设计问题
（实现的人遇到问题时写在这里，然后停下）

## 验收意见
（Claude 验收时写在这里）
```
