# 3.46 平台会话头像与图片缓存

状态：待评审（前端已完成）
设计：维护者 2026-11-26 指令；可参考 MaiBot 公开源码

## 目标

平台会话里的用户头像与图片重复进入会话时不再重复下载，提升切换与滚动性能。

## 实现

1. 前端：头像与图片按 `(平台, 发送者)` / 图片标识缓存为 object URL 或内存 Map，同一会话内复用；离开会话后可保留有限数量，按 LRU 清理。
2. 后端：头像与图片响应加合适的 `Cache-Control`（同源、私有、带 max-age），配合浏览器缓存；仍按权限校验，撤权后不再返回。
3. 不改权限与撤权语义；缓存按登录会话隔离，退出清空。
4. 与 3.41 的图片预览、3.43 的实时推送兼容。

## 前端实测（2026-11-26）

实现：头像按 `(platform, sender_id)`、图片按 `(source, id, position)` 缓存为 object URL，
放在 `inboxAvatarCache` / `inboxImageCache` 两个 Map 里；每次读取把条目移到队尾，按
最近使用顺序淘汰。上限：头像 128 条 / 8 MB，图片 40 条 / 32 MB；缓存 30 秒后过期，
与后端 `Cache-Control: private, max-age=30` 一致。切会话只断开懒加载观察和预览，
不清缓存；退出登录走 `clearInboxMediaCache()` 撤销全部 object URL 并清空 Map。图片仍用
IntersectionObserver 懒加载（root 为 `#inbox-messages`，提前 400px），不一次性下载长会话
的全部图片。

- 请求次数：用 4 条伪造消息（同一发送者 2 条、Bot 1 条、无发送者 1 条）和返回 PNG
  blob 的假 `fetch` 测试。4 个头像只发出 2 个请求（同发送者去重），`inboxAvatarCache.size=2`；
  整页重渲染后请求数仍为 2。图片第一次渲染发出 1 个请求，`inboxImageCache.size=1`；
  再次渲染同一图片不发新请求。
- 会话隔离与撤权：`clearInboxMediaCache()` 后两个 Map 都为空，再渲染会重新请求；
  之后到达的旧请求因 generation 不一致被丢弃。缓存 30 秒过期，过期后重新请求会再走
  后端权限校验；浏览器 HTTP 缓存也由后端 `private, max-age=30` 控制。真实 QQ 撤权事件
  未在假器官实例上复现，按后端 30 秒窗口设计。
- 预览与推送：图片预览弹窗使用缓存的 blob URL，`inbox-image-dialog` 打开且
  `src` 为 `blob:`，截图 `E:/Temp/ui-shots/343-05-image-preview.png`；3.43 的 `inbox`
  事件会重新渲染消息区，头像/图片继续命中前端缓存。Console `exceptions=[]`、`errors=[]`。
- 截图：`E:/Temp/ui-shots/343-10-inbox-light.png`（同一会话头像/图片）、
  `343-08-inbox-dark.png`、`343-09-inbox-narrow.png`。
- 环境偏差：假器官实例没有真实 QQ 收件箱，用伪造消息和假 `fetch` 验证缓存逻辑；原 18770
  和正式 28976 未改动。按维护者要求未跑 pytest。
