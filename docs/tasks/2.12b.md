## 接口

通用规则：新接口都在 `create_app` 里注册，依赖 `require_ready`（没登录 401，默认口令 403，和设置页一样），都是 `async def`。错误的 `detail` 一律是中文字符串（页面原样显示，docs/tasks/2.12.md 第 8 条），所以不用 FastAPI 自带的请求体校验（它报英文列表）：请求体先当普通字典收，交给下面的校验函数。

### 模型配置（`aureus/organs/model_config.py`）

```python
ReasoningLevel = Literal["none", "minimal", "low", "medium", "high", "xhigh", "max", "default"]
```

- `ModelConfig.reasoning_levels: tuple[ReasoningLevel, ...] = ()`：这个模型支持哪几档，不写就是不支持。
- `OrganConfig.reasoning_effort: ReasoningLevel | None = None`：器官选的一档；`ModelRoute.reasoning_effort` 原样带上。
- `ModelsConfig._check_references` 加一条：器官选了档位，它 `models` 里的每个模型都必须在 `reasoning_levels` 里列出这一档，否则报「器官 X 的思考等级 high 不是模型 Y 支持的（没写 reasoning_levels 就是不支持）」，不悄悄忽略。
- `llm_adapter.py`：路线上的 `reasoning_effort` 不是 None 时，调用 litellm 时加 `reasoning_effort=` 参数；是 None 时不传。八档取自 litellm 1.109.1 的 `completion` 签名，升级 litellm 时要核对。
- 新增公开函数 `validate_models_config(raw: Mapping[str, Any], source: str) -> ModelsConfig`，`load_models_config` 内部也调它。校验失败抛 `ConfigError`，文字和现在一样（现有测试不改），只是开头的来源说明由 `source` 给：读文件时是「模型配置文件 路径」，网页提交时写「提交的模型配置」，不要把本机路径返回给页面。

### 时间线（`aureus/timeline/`）

`TimelineQuery` 加两个字段，默认值保证现有调用不变：`before_id: int | None = None`（只要序号小于它的）、`since_time: datetime | None = None`（只要时间不早于它的）。库里的时间怎么存要先看 `database.py`，比较的两边格式必须一致（都转成 UTC）。和 `latest=True` 一起用时，仍是取符合条件的最新 N 条、按序号升序返回。

### 回复用的最近对话（`aureus/heartbeat/conversation.py`）

回复用户时取最近对话的那个 `TimelineQuery`（第 280 行附近）抽成模块级函数 `recent_dialogue(timeline, *, visibility, limit) -> Sequence[TimelineRecord]`，原处改成调用它，行为不变。时间线接口用同一个函数算分隔线，两边不会各算各的（D84 第 4 条）。心跳新增只读的 `context_message_limit() -> int`：此刻回复用户会带几条，即当前回复做法的 `message_limit`。`main_loop.py` 净增不超过 15 行。

### GET /api/timeline（`aureus/web/timeline_api.py`，新）

查询参数：`hours`（默认 24，1 到 720，从 `clock.now()` 往前数；`create_app` 新增 `clock` 参数，`assemble.py` 传核心用的那个时钟）、`before_id`（翻页）、`limit`（默认 100，1 到 300）、`types`（事件类型，逗号分隔，不写就是全部）。取符合条件的最新 `limit` 条，按序号升序，返回：

```json
{
  "records": [{"id": 1, "time": "ISO 8601", "actor": "user|me|person|system", "actor_id": "", "event_type": "message", "content": "", "visibility": "user_only", "channel": "web", "metadata": {}}],
  "next_before_id": 123,
  "context": {"message_limit": 20, "boundary_id": 101}
}
```

- `next_before_id`：取满了 `limit` 条时是这一批最早一条的序号，没取满是 null（这个时间范围里没有更早的了）。
- `channel` 取 `metadata` 里的 channel，没有就是空串。
- `boundary_id`：用 `recent_dialogue` 取 `context_message_limit()` 条对话，其中最早一条的序号，没有对话是 null。可见范围用回复已验证用户时同一个值（先看 `target.visibility` 在哪里定，不要自己写死）。页面把序号大于等于它的对话画在「当前上下文」一侧。
- 响应里没有 summary 字段：滚动摘要还没有，等它设计时再加字段（D84 第 4 条）。
- 「全部时间线」包括只有它自己可见的记录（想法、日记、状态变化）：能打开网页的只有登录的用户本人，观察台也看得到这些；每条带 `visibility`，页面可以标出来。这是 Claude 定的，评审时可改。

### GET /api/overview（同一个文件）

返回 `state_text`（心跳的 `describe_state()`）、`thinking`（`is_thinking`）、`energy_level`（可为 null）、`energy_tier`、`current_task`（后三项来自 `cognitive_state`，还没跳过第一拍时是 null、空串、空串）、`restart_required`（见后面「配置文件的写入」）。先看这几个是方法还是属性。

### 配置文件的写入（`aureus/common/toml_edit.py`，新）

模型配置和运行配置都是用户手写、带注释的 toml，网页改它们不能把注释洗掉。

- `apply_toml_edit(path: Path, edit: Callable[[TOMLDocument], None], validate: Callable[[dict[str, Any]], object]) -> None`：用 tomlkit 读入（文件不存在就从空文档开始），交给 `edit` 就地修改，再 `unwrap()` 成普通字典交给 `validate`（不合格抛 `ConfigError`，文件没动），通过了才写：同目录临时文件、`flush` 加 `fsync`、`os.replace` 换掉原文件。任何一步失败，原文件原样保留，临时文件清掉。换行符沿用原文件（有 CRLF 就继续用，文件不存在时用 LF）。
- `identity/editor.py` 里已经有一份保留注释的写回，先读它：能抽出来的部分挪进这里，`editor.py` 改成调用它（行为不变，现有测试不改）；抽不出来就两边各留，在「待设计问题」里写原因。
- 只在用户点保存时写。接口都是 `async def`，同一个进程里不会有两个请求同时写；别的进程（用户手改文件、`aureus keys`）不加锁。写入以文件此刻的内容为底，不是以页面加载时的样子为底。已知限制：模型配置是整份提交的，页面打开期间用户手改了文件，手改的条目会被覆盖。
- `restart_required`：`ConfigService`（`aureus/web/config_files.py`，新）里的内存标志，任何一次写成功后置真，进程重启自然清零。用户手改文件不会置真。`/api/overview` 和各个写接口的响应都带它。

### GET /api/models

返回 `{"exists": true, "config": {...}, "choices": {...}, "key_status": {...}}`：

- `exists`：models.toml 在不在。不在时 `config` 是 `{"config_version": 1, "providers": [], "models": [], "organs": {}}`，不报错：页面要能从零开始配。
- `config`：`ModelsConfig.model_dump(mode="json")`，默认值都补全了（页面显示的是生效的值）。读文件或校验失败返回 422，`detail` 是 `ConfigError` 的文字；传给 `validate_models_config` 的 `source` 写 "models.toml"，不带本机完整路径。
- `choices`：`{"protocols", "kinds", "strategies", "reasoning_levels"}` 四个列表，用 `typing.get_args` 从 `model_config.py` 的 `Literal` 取，web 里不再抄一份。
- `key_status`：`{密钥名: bool}`，每个服务商的 `api_key_env` 现在有没有密钥。取法在后面「密钥」一节定，这里调 `ConfigService.key_status(names)`，只返回 bool。

### PUT /api/models

请求体：`{"config": {...整份模型配置}, "password": "..."}`，`password` 只在下面第 3 点的情况下需要。

1. 校验：`validate_models_config(body["config"], "提交的模型配置")`，不合格返回 422，文件不动。写文件时 `config_version` 沿用文件里的，文件不存在就写 1。
2. 写回用 `apply_toml_edit`，按条目比较：服务商和模型按 `name`、器官按器官名，和文件此刻的内容比。没变的条目不碰（连注释原样不动）；变了的整条替换（这一条里的注释会丢，已知限制）；新增的追加；提交里没有的删除；顺序跟着提交走。
3. 要口令（Claude 提出，D84 第 6 条没写，评审时确认后补进 D84）：提交让某个已有服务商的 `base_url` 或 `api_key_env` 变了，或者新增了带 `api_key_env` 的服务商，就要口令，因为密钥会被送到新地址，局域网里的一次登录不该就能做到这件事。口令走 `auth.confirm_password`，错 403「口令不对。」，被限流 429，和设置页一致。其他改动（模型、器官、思考等级）不要口令。
4. 返回 `{"ok": true, "restart_required": true}`。提交和文件里的内容一样时不写文件，`restart_required` 保持原值。

### 密钥（`ConfigService` 在 `config_files.py`，路由在 `config_api.py`）

先读 `common/vault.py`、`organs/api_keys.py`、`cli/keys_command.py`。web 不能 import cli（import-linter）：`keys set` 里「没有密钥库就自动创建主密钥和密钥库」的逻辑如果在 cli 里，挪到 `organs/api_keys.py` 或 `common/vault.py`，cli 改成调用它（行为不变，现有测试不改）。

- `GET /api/keys` 返回 `{"vault": "ok|none|unreadable", "names": [...]}`。`none` 是还没有密钥库；`unreadable` 是打不开（有 vault 没有 key、被改动、版本太新），此时 `names` 是空。只列名字，不列值。
- `ConfigService.key_status(names) -> dict[str, bool]`：每个名字现在取不取得到非空的值，来源顺序和 `KeyResolver` 一样（环境变量 > 密钥库 > .env）。每次现读文件，不用启动时解开的那份，这样新录的马上显示「已设置」（要重启才用得上）。
- `PUT /api/keys` `{"name", "value", "password"}` 和 `POST /api/keys/remove` `{"name", "password"}`，规则：
  1. 来源不是本机（`auth.py` 里的 `is_loopback`）返回 403「密钥只能在本机的网页上录入。其他设备请到本机的网页，或用 aureus keys set。」这一条放在口令检查之前：别的机器不能拿这个接口试口令，也不消耗限流。假设前面没有反向代理（D53 是局域网直连），写进文档的已知限制。
  2. 口令必须是当前口令，错 403，被限流 429。
  3. `name` 要匹配 `API_KEY_ENV_PATTERN`；`value` 去掉两端空白后不能为空，不超过 `MAX_KEY_CHARS`（新常量，4096，没有实测依据，只为挡超大请求）。不合格返回 422，`detail` 是中文，不回显 `value`。
  4. 密钥库打不开时返回 422 并说明原因，不自动重建、不回退（D36 7.2）；没有密钥库时 `PUT` 创建它；`remove` 的名字不存在返回 404「没有这个密钥。」
  5. 写密钥库要等文件锁最多 10 秒（D36 7.2），而接口是 async def、和心跳在同一个线程，所以写密钥库必须用 `asyncio.to_thread` 放进线程，不能卡住心跳（D41 第 3 条）。线程里不碰 SQLite 连接。
  6. 响应只有 `{"ok": true, "restart_required": true}`。任何响应、日志和报错里都不出现 `value`：请求体按字典收，不用会在 422 里回显输入的 pydantic 模型；运行中的日志过滤器不认识刚录入的新值，所以代码绝不能把它写进任何日志。

### 运行配置（`ConfigService` 在 `config_files.py`，路由在 `config_api.py`）

`aureus/common/config.py` 新增公开函数 `validate_runtime_config(raw: Mapping[str, Any], source: str) -> RuntimeConfig`，`load_runtime_config` 内部也调它。规则同模型配置：失败抛 `ConfigError`，文字不变，来源说明由 `source` 给，不把本机路径返回给页面。

#### GET /api/config

返回 `{"exists", "config", "schema", "readonly", "password_sections"}`：

- `exists`：aureus.toml 在不在。不在时 `config` 是全部默认值，不报错。
- `config`：`RuntimeConfig.model_dump(mode="json")`。读的是文件，不是运行中的值：刚改过还没重启时两者不一样，`restart_required` 为真就是这个意思。
- `schema`：`RuntimeConfig.model_json_schema()`（含 `$defs`）。页面靠它知道每个字段的类型、范围、默认值和可选值，后端不另写一份字段表。字段的中文名和说明写在页面里；页面遇到不认识的新字段，要照字段名显示，不能崩。
- `readonly`：`["config_version", "web.enabled", "web.allow_remote", "web.port"]`。D84 第 6 条只列了后两项；`web.enabled` 关掉后重启，网页就打不开了，同样会把人锁在外面，Claude 一并列入，评审时确认后补进 D84。
- `password_sections`：`["safety", "web"]`。
- 文件读不了或校验失败：422，`detail` 是 `ConfigError` 的文字，`source` 写 "aureus.toml"。

#### PUT /api/config

请求体 `{"changes": {"diary": {"write_after_hour": 21}, "log_level": "DEBUG"}, "password": "..."}`。`changes` 只写要改的字段：顶层标量（目前只有 `log_level`）直接写值，其余写成 `{节: {字段: 值}}`。按下面的顺序处理，哪一步不过就在哪一步返回，文件不动：

1. 形状：值只能是布尔、整数、浮点数、字符串；null、列表、嵌套超过一层都返回 422「配置的值只能是开关、数字或文字。」
2. 去掉没变的：以文件此刻的内容为底（文件不存在就是全部默认值），和它相同的字段直接忽略，既不算改动，也不检查口令。页面整节一起发也没关系。
3. 只读项：剩下的字段里有 `readonly` 里的，返回 403「这一项只能在本机直接编辑 aureus.toml：改错了会让你从网页上进不来。」这一条放在口令检查之前，不消耗限流。
4. 口令：剩下的字段里有属于 `password_sections` 的，就要 `password`，走 `auth.confirm_password`，错 403「口令不对。」，被限流 429，和设置页一致。别的节不要口令。
5. 校验：把剩下的字段套在文件此刻的内容上，整份交给 `validate_runtime_config(..., "提交的配置")`。不认识的节和字段、范围不对、跨字段的规则（比如 exploration 开着要求 interests 开着）都在这里报，422。
6. 写回：用 `apply_toml_edit` 逐个字段就地改，节不存在就新建；没动的字段、别的节和注释原样不动。文件里这个字段原来只是一行被注释掉的默认值，就在这一节末尾追加新的一行，不去改那行注释。
7. 返回 `{"ok": true, "changed": ["diary.write_after_hour", "log_level"], "restart_required": true}`，`changed` 是实际改了的字段名（顶层字段只写名字）。没有任何字段变化时不写文件，`changed` 是空数组，`restart_required` 保持原值。
8. 日志：写成功后用应用日志记一行，只写字段名，不写值（D84 第 6 条）。不写时间线。

## 行为细则和边界情况

1. **登录检查**：新接口一律依赖 `require_ready`：没登录 401，默认口令 403。只有 `/` 首页不检查，页面里不能出现数据，现有的首页测试照样要过。
2. **密钥不泄露**：任何响应、应用日志、422 的 `detail`、异常追踪里都不能出现密钥原文。`PUT /api/keys` 的请求体按字典收，校验失败的文字里不带 `value`；`ConfigService` 的日志只写密钥的名字。
3. **失败时文件不变**：校验不过、写临时文件失败、替换失败，原文件都原样保留，临时文件清掉。磁盘错误（`OSError`）返回 500「写不进配置文件。」，不带本机路径。出错朝安全方向倒：拿不准能不能写，就不写。
4. **不卡住心跳**（D41 第 3 条）：口令检查要用和心跳同一个 SQLite 连接，留在事件循环线程里，先做；过了之后，读写配置文件和密钥库这类只碰文件的事放进 `asyncio.to_thread`。线程里不碰 SQLite 连接，也不碰心跳对象。
5. **参数超范围不报错**：`hours`、`limit` 像 `/api/history` 的 `limit` 一样夹到范围内；`before_id` 小于 1 当作没写；`types` 里的空项忽略。
6. **时间线接口只读**：不写时间线，不改任何状态；`metadata` 原样返回，不裁剪。
7. **页面提交的永远只是密钥的名字**：`api_key_env` 沿用现有的 `API_KEY_ENV_PATTERN` 校验，不合格 422。密钥本身只走 `PUT /api/keys`。
8. **网页写的配置不比手写的宽松**：下次启动读配置走的还是原来的校验；启动流程本身不改。
9. **Windows 上的 `os.replace`**：目标文件被别的程序打开着时会失败（编辑器占着文件），按第 3 条处理，返回 500，原文件不动。
10. **不加新依赖**：tomlkit 已经在依赖里，其余用标准库。

## 坑

- 换行符：docs 多为 CRLF，代码和 main_loop.py 用 LF，全部 UTF-8。`toml_edit` 改配置文件时沿用原文件的换行，不要统一成 LF；写 Markdown 文档时也先看原文件用哪种。
- 完整检查约 3.5 到 5 分钟，测试运行中不要修改 aureus/、tests/。
- Windows 上 `os.replace` 目标文件被编辑器占着会失败，按「行为细则」第 3 条返回 500，原文件不动；测试里用补丁让它抛 `OSError`，不要真去占文件。
- tomlkit：校验用的是 `unwrap()` 之后的普通字典，不是 tomlkit 的包装对象，否则 pydantic 可能认不出类型；改完写回的才是文档对象。原来只是被注释掉的默认值那行，tomlkit 不会把它当成字段，所以新值只能追加在节末尾，这是预期行为。
- `RuntimeConfig` 里不少节是 `strict=True`：`true` 不能冒充整数，字符串 `"1"` 不能冒充数字。页面传值的类型要对，后端报的 422 `detail` 照实返回。
- `ModelsConfig.model_dump(mode="json")` 会把元组变成列表，页面提交回来的也是列表，校验时 pydantic 会转回元组，不用特殊处理。
- 测「只能本机」要伪造来源地址，先看 `tests/web/test_auth.py` 里怎么做，不要给被测代码加只在测试里用的开关。
- 思考等级那八档来自 litellm 1.109.1 的 `completion` 签名，升级 litellm 时核对；web 里不要再抄一份，从 `model_config.py` 的 `Literal` 用 `typing.get_args` 取。
- 日志过滤器只认识启动时已知的密钥，刚通过网页录入的新值它不认识，所以代码绝不能把 `value` 写进任何日志，包括 debug 日志和异常追踪。
- 测试里的密钥一律用编造的假值；不读 secrets.key、secrets.vault、.env 和 aureus_home/，不打印密钥，不真实调用模型。
- 现有的 `tests/web/` 和 `tests/monitor/` 必须全部通过：界面由用户在另一个会话里改，后端接口表要和 docs/tasks/2.12.md 保持一致。
