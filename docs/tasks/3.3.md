## 交付

从显式实例的迁移暂存记录发布人物与关系到独立 Aureus 数据目录。由人际子系统拥有并读写其表，正常会话可按当前发言人的平台账号取回历史称呼、印象及关系依据。复用现有人物目录。优先核对目标版 MaiBot 的人物识别逻辑；若采用项目原有的账号主键作为等效实现，记录该取舍及来源位置。

1. 合并 `person_info` 与附属 `person_state` 时优先用明确的平台、账号及来源人物键。保留原称呼、印象、记忆点、认识时间、关系状态以及可追溯键。人物原有的平台账号可以对应到已存在的同一人。仅有名字时保留来源人物，禁止据同名连到另一个账号。来源时间或说话人缺失保持缺失。
2. 导入 `relation_edge` 的双方、方向、关系类型、权重、证据与时间。附属 `events`、`thread_item` 的人物引用和摘要可查询。无法确认一端时保留原始记录及原因，不强行连边。导入历史权重应保留原量纲，只有实测或上游实现证实与现有好感刻度等价才复用；已有好感流水保持只追加。
3. 真实入口可从平台账号取回历史认识的信息，并在相关人物的回复上下文中按已有预算选入有出处的材料。多人同名、跨通道同一人、无结果均要覆盖。来源正文作为聊天资料处理。用户身份仍由本机原配置认定。
4. 使用稳定来源键实现可重复发布，失败后重跑不重复建人或连边。按来源表分别报告写入、已存在、待解析及原因，并验证目标重启仍可读取。
5. 只迁习得数据。不得访问或复制 MaiBot 配置，不调用 Aureus 人格编辑或建立人格版本；用模拟已配置目标证明迁移前后身份文件逐字节一致，版本记录数量与内容相同。

## 实现取舍

核对 MaiBot v1.3.15（`062d45c`）的 `src/person_info/person_info.py` 中的 `get_person_id`、`Person` 与 `resolve_person_id_for_memory`，以及 `src/common/utils/utils_person.py` 中的 `get_person_info_by_user_id_and_platform`。上游按平台和账号生成稳定人物键，部分记忆查找可从名字回退。Aureus 复用现有 `accounts` 的平台与账号主键认人，原人物键用于关联同一实例明确引用的人物及追溯，姓名仅保留为资料。历史权重沿用来源量纲，好感账仍走原来的互动接口。

## 发布命令

```text
aureus migrate-maibot publish-people --instance INSTANCE STAGING.sqlite AUREUS_HOME
```

从 3.2 已暂存的主库 `person_info` 和人际库 `person_state`、`relation_edge`、`events`、`thread_item` 取资料。来源键直接保留 `source_rows.source_key` 的 JSON 数组表示，按实例、来源表和原始主键对账。显式目标要有自己的 Aureus 身份配置，发布时先按正常启动的规则登记本机用户的账号，再以一个事务写入人际资料。发布结果按表给出暂存、写入、已存在、待解析与原因，合计覆盖本次选择的暂存行。

## 3.6a 提示词登记

固定模板为 `aureus/heartbeat/people_context.py` 的 `PEOPLE_CONTEXT_TEMPLATE`，唯一变量为 `people_records`。真实组装链为 `ConversationFlow._reply` → `format_people_context` → `build_reply_prompt` → `OrganRequest.prompt`。在回复器的用户消息中，位置在当前对话及可选的长期记忆引用之后、规划意图及长度要求之前。正常回复的规划后和合并调用路径都使用它。开关为 `[people].history_in_reply_enabled`。匹配当前发言人、有可用资料且召回共享字符预算有余量时呈现。完整预览用具名占位符模拟 `people_records`，无需读取运行库。标签为内部资料，来源格式为 `[来源表 #人际资料编号]`，每条可通过 `PeopleDirectory.history_for` 对照原始来源键。
