# 路线图 3.5 · 长期记忆

状态：实现中

先读 D80、D89、[迁移基线](../13-references-and-migration.md)、[3.2](3.2.md)、现有 MemoryIndex、心跳的 recall 与记忆注入。实际部署为 A_Memorix 2.0.0，迁移版本 27。优先复用其存储、检索和证据组织代码，对照所装版本的源码与许可，注明具体调用点。

## 交付

1. 明确读取 3.2 产物，按实例和来源键发布历史消息、段落、episode、事实、证据、关联以及照片描述等可用记忆。保留原文、说话人、时间和时间精度、溯源指针及状态。对缺失、失活、矛盾、删除与过期记录区分归档和有效召回。组装证据链时处理孤立引用，逐表对账。媒体文件与原始附件按可验证引用归档至私有目的目录，保留找不到文件的准确诊断，导入不执行文件内容。
2. 迁入的资料和日后积累的资料属于一个记忆库。按人物、时间、查询词和相关性召回，允许一次查询找到来自群聊、私聊和无会话号的经历。检索和刷新在真实调用链工作，沿用时钟与容量预算。已有时间线仍只追加，不伪造过去发生在 Aureus 的事件。
3. 对照 MaiBot 启发式记忆注入和显式 query_memory 两条路径，将适量的有出处材料送达 Planner 或 Replyer。验证 Replyer 实际收到符合当前查询的材料，不能依赖上游关闭的 retro prompt。保留原库与核心事实，可由原数据重建使用的全文或向量派生索引。涉及外部嵌入与模型调用的验证使用本地模拟。
4. 在独立工作树先做可独立验证的记忆存储、状态过滤、检索和证据格式。3.2 接口就绪后用正式包及暂存表走通发布。按积累量触发整理，避免心跳同步扫描全库。

## 自检

- [ ] 单一人物在不同通道及无会话号的一个月前事件可按内容及时间查回，原文、人物与证据准确；同名者不会混淆。模拟已删除、失活和替代事实不成为当前事实回答。
- [ ] 经 CLI 导入，重启后查询；删除合成目标的派生索引并重建，恢复相同有效命中。重复发布对账相等。
- [ ] 假器官记录两条检索入口的真实上下文与空结果处理；生成新经历后历史与新记忆均可检索。
- [ ] 记下复用位置、适配差异、逐类覆盖与实测限制，运行专项和质量检查。

## 范围

群聊实发属于 3.9，语言学习及账号关联分别见 3.4、3.6。用户人设及源库只读。

## 实现对照

- A_Memorix 2.0.0 的 `metadata_fact.py::list_current_person_fact_claims` 按有效状态和左闭右开时间段取当前事实。适配点为 `memory/history.py::search_history`，用 Aureus 时钟判断有效期。原件可按来源读回，全文索引是可重建的 SQLite 派生表。
- MaiBot 1.3.15 中 `heuristic_injector.py::build_injection_message` 和 `query_memory.py::handle_tool` 均调用 `MemoryService.search`。Aureus 启发式入口独立开关默认关闭，开启后用本轮回忆提示构造词项，搜索走后台线程。显式查询仍采用 Planner 建议，Replyer 优先使用显式结果。两条入口沿用 D80 的条数和 900 字预算。
- 从安装版 `MemoryService.get_person_profile` 追到 `person_profile_service.py::query_person_profile`：非空人工正文优先于自动结果，自动快照仍保留。该服务的别名覆盖行存在即采用人工列表，空列表也有意义；`person_profile_active_persons` 只记录已开启范围的活跃人物。自动快照按 `profile_version` 选最新版并检查有效期。两类人工覆盖应由 3.2 以业务行导出，均按 `person_id` 对账；其他人的画像归 3.3 整合。
