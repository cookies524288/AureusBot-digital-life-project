# 3.15a · 规划器调用工具

状态：实现中。设计：D103。先读 [总任务](3.15.md)、`aureus/organs/interface.py`、`llm_adapter.py`、`aureus/heartbeat/conversation.py`、`planning.py` 和根目录 `Planner tool prompt.txt`。

## 子步骤

1. 协议：请求带声明过的工具，响应带已解析工具名、调用 ID、参数；真实适配器透传并保留耗用和错误处理，无工具时其他器官完全不变。处理纯工具响应及分段到达的参数，不能把工具结果当普通回复。合成夹具覆盖普通和流式响应。
2. 调度：明确的 `reply` 才能调 replyer，`stop`、无调用、失败和错误参数均不发言；有界读取工具返回结果再规划，保留原资源权限、预算、再审、防抖和分段。用指定模板的结构、措辞和实际可用工具生成提示，先判断「是否在对我说话」，结论随参考回复进入 replyer。简单原因摘要用于展示，不记录隐式推理。工具表和处理器共源，无真实能力不声明；不得开放 shell、外部子代理或任意工具服务。
3. 展示：planner 配置菜单的“工具列表”使用同一服务端目录，只显示实现且可用的工具、用途及参数，沿用器官面板视觉与可访问交互。

## 工具协议

- `OrganRequest.tools` 传 `ToolDefinition`；`OrganResponse.tool_calls` 返回 `ToolCall`，参数已经解析成 JSON 对象。器官只检查调用 ID、工具是否声明、参数对象和流式协议，不执行工具；具体参数规则由调度器校验。无调用时只返回普通文本（若有），它不是发言决定。任一调用损坏、重复或未声明时，整批不交给调度器，`metadata["tool_calls_invalid"]` 为 `True`，已产生的耗用仍计账。
- 调度器要继续同一轮规划时，保留原请求文字，向 `OrganRequest.tool_history` 依序追加 `ToolExchange`：每批完整的助手调用后接由 `ToolResult.call_id` 关联的结果。适配器在最后的用户消息后按独立助手／工具角色发送，不把工具结果或上一轮规划文字拼成聊天回复。
- 正常一轮只能发出一次终止选择：`reply` 提交内部回复参考及指向判断，`stop` 不带参数且不发言；收件箱已启用时可单独用 `inbox_attention` 提交静默建议。`query_memory` 只在记忆召回可用时声明，一轮最多查一次、再规划一次。多调用、无调用或任一参数不合法时整轮不发言。精力和激素只影响建议，不取代 `reply`。

不做：改主动探索或平台接口、记录模型私有思考、用真实模型验证。独立可运行步骤各交一个提交，由主审负责发布。
