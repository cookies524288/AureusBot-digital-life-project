## 交付

1. 配置显式启用的 QQ 通道，接入正常启动和关闭。端点、账号标识从部署配置取得，凭据走既有密钥接口。默认关闭；测试使用内存或回环模拟端。依已有 transport 协议收发 JSON，动作与 echo 对应，处理失败、断连、超时和关闭。心跳不因网络停住。
2. 群聊、私聊、点名、引用、消息 ID、实际发言人与目标地址保持正确。多位说话人的回复回到原群并保留正确引用。用平台、接收账号及消息标识识别重复输入，包括断线重放；本机发出的回显只处理一次。回复经过识人、注意力、规划与安全网关。投递地址不是记忆分区。
3. 网页与 QQ 的账号关联通过短时、单次、可撤销或过期的验证码及已验证用户会话完成。仅能绑定实际证实控制的账号；冲突、重放、超时皆覆盖。按现有人际接口写账号映射，避免同名合并或误授用户身份。测试使用假时钟，无需真实送达。
4. 记录外网访问网页的部署选项、鉴权及 TLS 前提，沿用既有私有绑定默认。专注判断可行部署路径，本步不发布公网服务。

## 实现约定

- SnowLuma 采用正向 WebSocket 和 `send_msg`，使用 `get_login_info` 核对接收账号。动作逐条匹配 echo，失败和超时记应用日志，断连后的发送不补发。QQ 只接收文本、点名和引用，自己发送的事件由已生成的回复记录代表。
- 以平台、接收账号和消息 ID 去重，最近 16,384 个键在同一通道实例的重连间保留。投递地址用于注意力分批和回复路由，实际发言人按 QQ 账号认人。原平台时间、引用和投递地址随入站消息记入同一时间线。
- 网页填写预期 QQ 号，生成有效期五分钟的验证码。该号须在普通 QQ 私聊中发送验证命令，发起的网页登录会话再确认写入。已有独立人物档案时保持冲突，由 3.3 与 3.6 整合时处理。用户身份仅用于已验证账号的普通私聊，群聊和临时私聊保持外部对话权限。
- 正常启动路径复用已有核心、身份、记忆与安全网关。网页私聊历史限用户私聊。部署路径与 HTTPS 前提见[迁移说明](../13-references-and-migration.md)，许可证与协议出处见[第三方清单](../../THIRD_PARTY.md)。
