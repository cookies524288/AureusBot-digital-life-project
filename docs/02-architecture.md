# 02 · 总体架构

> 本文描述 AureusBot 由哪些部分组成、它们怎么配合，以及它在你电脑上是怎么跑起来的。

---

## 1. 总览

```text
外部世界：用户、网友、各平台、互联网、其他 agent
      │ 消息、事件                          ▲ 消息、动作
      ▼                                     │
  通道 channels                         行动 actions
      │ 感知                                ▲ 通过安全检查的决定
      ▼                                     │
  核心（只有一个，一直在跑）
  │
  │  心跳 heartbeat → 注意力 attention → 器官 organs → 决定 → 反馈 feedback
  │
  │  状态：身份 identity · 身体 body · 激素 hormones · 心情 mood · 日程 agenda
  │  经历：时间线 timeline · 记忆 memory · 人际 people · 技能 skills
  │
  安全 safety 贯穿所有层：权限 · 审批 · 审计 · 预算上限 · 急停
```

一句话：**外界的一切先经过通道变成"感知"，进入核心；核心按自己的节奏决定做什么，经过安全检查后由行动层执行；结果作为新的感知回到核心。**

---

## 2. 四组子系统

| 分组 | 子系统 | 作用 |
|---|---|---|
| 我是谁 | 身份、身体、激素、心情 | 它是谁、想成为谁；身体状态如何；此刻的情绪、整体的心情 |
| 我的经历 | 时间线、记忆、人际、技能 | 发生过什么、记得什么、认识谁、会什么 |
| 我怎么想、怎么做 | 心跳、注意力、日程、器官、行动、反馈 | 什么时候想、想什么、怎么做、做完学到什么 |
| 我和世界 | 通道、安全 | 和外界接触的途径，以及守住边界 |

每个子系统的详细职责见 [03-subsystems.md](03-subsystems.md)。

## 3. 心跳：主循环

心跳是 AureusBot 的主循环，一直在跑。每一拍做这些事：

| 步骤 | 做什么 | 花不花钱 |
|---|---|---|
| 1. 量身体 | 更新身体信号：读账本、负荷、故障记录、时钟 | 不花，纯代码 |
| 2. 收感知 | 收集各通道的新消息、行动结果、到期日程，写入时间线 | 不花 |
| 3. 定焦点 | 注意力按规则挑出此刻最该处理的一件事 | 不花 |
| 4. 想一想 | 组装上下文，调用规划器，得到建议：做不做、做什么、预期是什么；要说话时再由回复器写成拟人的话 | 花钱，只在需要时 |
| 5. 过安检 | 检查权限、预算和风险等级，必要时请示用户 | 不花 |
| 6. 去做 | 行动层执行，结果作为新感知回到第 2 步 | 视行动而定 |
| 7. 对结果 | 反馈：对比预期和结果，更新自信、激素、心情、技能、人物印象 | 偶尔花（需要判断时） |
| 8. 没事时 | 按身体状态选择休息、整理、推进日程或找人聊 | 视情况而定 |

节奏：有新感知时立即跳一拍；没有时定时跳（例如每分钟一次），只做第 1–3 步和第 8 步的判断。

**心跳本身是普通代码，不花 token。只有需要思考时才调用器官。** 这是控制成本的关键。

## 4. 一条消息的旅程

举个例子：用户在网页上说"今天面试被拒了"。

1. **通道**：网页通道把它转成一条"感知"：来源是网页，账号是用户，可信度高，可见范围是"用户私聊"。
2. **时间线**：追加一条记录。
3. **注意力**：用户的消息优先级最高，成为当前焦点。如果它正在做优先级更低的事，那件事暂停排队。
4. **组装上下文**：身份事实和人设、身体状态摘要、用户的人物档案、相关记忆（比如上周提过在准备面试）、最近的时间线。只放用户可见范围内的内容。
5. **规划器**：给出建议——意图是安慰并问问细节，预期是用户愿意多说一些，不需要别的行动。
6. **回复器**：按表达风格把意图写成拟人的话：口语、短句，可能分两条发。
7. **安全检查**：通过。**行动**：经网页通道发出。
8. **反馈**：用户回复后，判断器官评估反应。预期达成，"愉悦"略微上升；用户的档案追加"面试受挫"；日程新增"过两天问问后续"。

## 5. 没人找它的时候

```text
空闲
 ├─ 精力低？                              → 休息，不发起任何花钱的事
 ├─ 夜间且空闲？                          → 整理：写日记、沉淀记忆、更新人物印象
 ├─ 日程里有到期的事？                    → 去做
 ├─ 社交需求高、时机合适、又有想说的事？  → 主动联系
 └─ 都不是                                → 按兴趣做点小探索（查资料、读文章），有收获就记进日程
```

"时机合适"由规则判断：不在用户的休息时段，今天主动联系的次数没超限；以后开启"用户状态"信号后，还会避开用户打游戏的时候。所有自主行为都受精力和频率上限约束。

## 6. 时间尺度

| 尺度 | 时长 | 做什么 |
|---|---|---|
| 反应 | 秒 | 回复消息、执行动作 |
| 情绪起伏 | 分钟 | 激素被事件触发，再按半衰期慢慢消退 |
| 日常 | 分钟到小时 | 推进日程、主动社交、小探索 |
| 睡眠整理 | 每天 | 写日记，然后回顾经历并调整人设（D80、D81）；记忆索引随时建，人物印象和技能复盘等对应阶段再定 |
| 成长 | 周到月 | 每周、每月回顾；技能积累、关系变化、对自己擅长什么的认识变化 |

## 7. 在你电脑上怎么跑

```text
你的电脑（例如一台带独立显卡的笔记本）
├── AureusBot 核心进程（Python，只能有一个）
│   ├── 通道：终端 / 网页 / 以后的 QQ 等
│   ├── 记忆：先用简易版，以后换成 A_memorix（作为库运行在核心进程里）
│   └── 器官：调用云端 API 或本地模型
├── 观察台（Streamlit，只读数据库）           给你看它的内部状态
├── 本地模型服务（Ollama，用显卡）           向量化、轻量判断
└── 它自己的电脑（Hyper-V 虚拟机，Phase 4）
    └── Windows-MCP                            它的"手"只在这里操作
```

笔记本合盖、关机时，它就真的在"睡觉"——醒来后会知道自己睡了多久。

如果以后想让它 24 小时在线，可以把核心搬到一台常开的小主机上，笔记本的显卡变成"有时在线的器官"。这是一个待定决定，见 [10-decisions.md](10-decisions.md)。

## 8. 它的"家"：数据目录

```text
data/
├── aureus.db      核心数据库：时间线、身体记录、人际、日程、反馈、账本、审计
├── logs/          运行日志（文本文件，按大小滚动；出问题时先看这里）
├── diary/         每日日记（Markdown，你可以直接打开读）
├── memory/        A_memorix 的数据
├── skills/        技能，每个技能一个文件夹
└── snapshots/     定期快照，用于恢复
config/
├── identity.example.toml  身份配置模板（进 git）
├── identity.toml          用户的个人设定：身份事实和四层人设（不进 git）
└── aureus.toml            运行配置：模型、预算、通道等
secrets.vault      加密的密钥库（D36），不进 git
secrets.key        主密钥（D36），不进 git
.env               旧的明文密钥，最低优先级回退（D36），不进 git
```

> 上图是**数据根目录**里的样子（D28、D31）：源码运行默认位于项目根目录的 `aureus_home/`，位置可由 `--home` 或 `AUREUS_HOME` 覆盖，见 [14-user-data.md](14-user-data.md)。升级软件保留此文件夹，移动项目时可整体带走。

**`data/` 就是它本身。** 备份 `data/` 就是备份它；同时运行两份 `data/` 是被禁止的，这就是"唯一"在工程上的含义。

## 9. 数据流规则

```text
通道只做翻译：不做决定，不存长期状态
器官只给建议：不直接写任何状态
状态写入必须走对应子系统的接口，并记入时间线
所有行动先过安全检查再执行，结果回到时间线
时间线只追加：不改、不删，更正也以新记录追加
身份事实和不变人格只有用户能改；另外三层人设它能按规则改，每次都留痕
所有"现在几点"都从时钟对象取，不直接读系统时间（实验时可以加速时间）
```

## 10. 可实验性

第一部分要做验证实验，所以下面四点从 Phase 0 起就是架构的一部分，不是事后补的测试代码：

| 能力 | 做法 | 用途 |
|---|---|---|
| 可注入时钟 | 所有子系统都从同一个时钟对象取时间 | 实验时加速时间，几小时跑完"一个月" |
| 可替换器官 | 器官接口统一，实验时可以换成"假器官"：返回预设结果，报告虚拟用量 | 不花钱、可重复地跑实验 |
| 机制开关 | 每个身体信号、激素、心情、反馈、注意力规则都能在配置里单独关闭 | 开关对比（消融） |
| 全量记录 | 状态变化全部进时间线，花费全部进账本 | 实验指标直接从数据库算出来，结果可复现 |

详见 [12-kernel.md](12-kernel.md) 第 6 节。

## 11. 关键设计决定

| 决定 | 理由 |
|---|---|
| 独立进程，不做 MaiBot 插件 | 唯一的个体必须位于所有聊天之上 |
| 平台只是通道，用户的主通道是自家网页 | 平台随时可能失去，也有各种限制 |
| 心跳是代码，器官按需调用 | 让它"一直在"，又不至于一直花钱 |
| 时间线只追加、带可见范围 | 连续性和信息边界的地基，事后补很难 |
| 身体信号挂在真实数据上 | 没有装饰 |
| 实验能力从 Phase 0 起内建 | 验证实验要可复现、成本低 |
| 器官支持多协议，用 litellm | D24 |
| 激素用代码实现，不交给大模型 | D20，"没有装饰" |

完整的决策记录见 [10-decisions.md](10-decisions.md)。
